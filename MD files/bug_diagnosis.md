## Bug 1: Virtual Tick Not Working (Sidebar always shows "Waiting for tick...")

### Root Cause
The Sidebar component ([Sidebar.tsx](file:///c:/PROGRAMER's%20FOLDER/Projects/RazorPay/RevenueGuard/dashboard/src/components/Sidebar.tsx#L46)) has the virtual date **hardcoded** as static text:

```tsx
<span className="text-white/90 font-mono text-sm">Waiting for tick...</span>
```

It never fetches or listens for the virtual date from the backend. The tick endpoint (`POST /api/simulation/tick`) does return `virtual_date` in the response, but the Sidebar has no way to receive it.

### Fix
1. Add a new backend endpoint `GET /api/simulation/state` that returns the current `simulation_state["virtual_date"]`.
2. In the Sidebar, use `useApi("/api/simulation/state")` to fetch and display the current virtual date.
3. The WebSocket `state_updated` event will trigger SWR to refetch, keeping it live.

## Bug 2: All Issued Invoices Stay at Stage 1 (Escalation stage never updates in DB)

### Root Cause
This is the **most critical bug**. Look at [core_loop.py](file:///c:/PROGRAMER's%20FOLDER/Projects/RazorPay/RevenueGuard/src/engine/core_loop.py#L27-L30):

```python
initial_state = {
    ...
    "escalation_stage": "STAGE_1",  # ← ALWAYS hardcoded to STAGE_1
    ...
}
```

And then in [nodes.py](file:///c:/PROGRAMER's%20FOLDER/Projects/RazorPay/RevenueGuard/src/graph/nodes.py) the `draft_email` node correctly computes the stage into `state["escalation_stage"]`, but **the core_loop never writes `escalation_stage` back to the database**:

```python
# core_loop.py line 51-53 — only updates status and promised_date
if final_state.get("new_status"):
    invoice.status = InvoiceStatus(final_state["new_status"])

if final_state.get("extracted_entities") and "promised_date" in final_state["extracted_entities"]:
    invoice.promised_date = ...
```

The `invoice.escalation_stage` column is never updated! So the DB always shows `STAGE_1`.

### Fix
In `core_loop.py`, after the graph runs, also persist the escalation stage and Razorpay link:

```python
if final_state.get("escalation_stage"):
    invoice.escalation_stage = final_state["escalation_stage"]

if final_state.get("payment_link_url"):
    invoice.razorpay_payment_link_id = final_state["payment_link_url"]
```

Also, the `initial_state` should read from the existing `invoice.escalation_stage` instead of hardcoding:

```python
"escalation_stage": invoice.escalation_stage or "STAGE_1",
```

## Bug 4: No Human-in-the-Loop

### Root Cause
There are **three places** human-in-the-loop should trigger, but none actually do:

1. **STAGE_4 gate (Missing):** In `draft_email` node ([nodes.py](file:///c:/PROGRAMER's%20FOLDER/Projects/RazorPay/RevenueGuard/src/graph/nodes.py#L80-L90)), when `stage_map` resolves to `"UNRESPONSIVE"`, the code just sets the status and returns. There is no `STAGE_4` path that triggers a "requires human approval" audit entry. The compliance rubric says *"STAGE_4: Formal final notice (requires human approval before sending)"* but it's never implemented.

2. **DISPUTE routing (Incomplete):** When a client reply is classified as `DISPUTE`, the `classify_reply` node sets `new_status = "DISPUTE"` but then the edge `route_after_classification` sends it to `execute_action` which just logs it. There's no `HUMAN_ESCALATED` status set or notification sent.

3. **Webhook handler (Stub):** The `POST /api/webhooks/razorpay` endpoint ([main.py](file:///c:/PROGRAMER's%20FOLDER/Projects/RazorPay/RevenueGuard/src/main.py#L103-L111)) is a **stub** — it just prints the event and broadcasts, but never actually updates any invoice status.

### Fix
1. Add `STAGE_4` to the `stage_map` in `draft_email` → sets status to `HUMAN_ESCALATED` and logs an audit entry saying "Requires human approval before sending".
2. In `execute_action`, when the status is `DISPUTE`, also log a `HUMAN_ESCALATED` audit entry.
3. **Implement the webhook handler**: parse the event type, find the invoice, and update its status accordingly:
   - `invoice.paid` → `RECOVERED`
   - `payment.dispute.created` → `DISPUTE`
   - `payment.failed` → no status change, but log an audit entry

## Bug 5: Invoice Progression Is Too Slow

### Root Cause
Multiple compounding issues:

1. **Cooldown is always OFF.** The `check_cooldown` node ([nodes.py](file:///c:/PROGRAMER's%20FOLDER/Projects/RazorPay/RevenueGuard/src/graph/nodes.py#L24-L27)) always sets `should_send_email = True`:
   ```python
   async def check_cooldown(state: RecoveryState) -> RecoveryState:
       state["should_send_email"] = True  # ← ALWAYS true, never blocks
       return state
   ```
   This means cooldown never fires, which is actually **good** for speed — the problem is elsewhere.

2. **Only 1 transition per tick per invoice.** Each tick calls `compiled_graph.ainvoke()` once per invoice, which walks through the graph once. The graph goes: `check_overdue → check_cooldown → retrieve_context → classify_reply → draft_email → evaluate_compliance → call_razorpay → execute_action → simulate_client → END`. 
   
   So in **one tick**, an `ISSUED` invoice can only go to `OVERDUE` (in `check_overdue`) and then to `NOTIFIED_1` (in `draft_email`). That's already 2 transitions in 1 tick, which is reasonable.

3. **The REAL slowness problem:** The `check_overdue` node only changes `ISSUED → OVERDUE`. But invoices that are *already* `OVERDUE` go through the full graph and advance to `NOTIFIED_1`. Then on the next tick, `NOTIFIED_1` invoices go through and advance to `NOTIFIED_2`. So it takes **3-4 ticks minimum** to fully escalate an invoice. With 100 invoices, each requiring an LLM call for `draft_email` and another for `compliance_judge`, each tick can take **minutes** if using a real API key.

4. **The "Auto-Run 30 Days" runs ticks in 1-second intervals**, but each tick might take 30+ seconds with LLM calls for 100 invoices. The `setInterval` fires the next tick before the previous one finishes, causing overlapping requests and potentially crashing.

### Fix
1. **Speed up the auto-run interval:** Change the auto-run to use sequential `await` instead of `setInterval`:
   ```tsx
   // Instead of setInterval with 1s
   for (let i = 0; i < 30; i++) {
     await apiPost("/api/simulation/tick", {});
     setAutoRunProgress(i + 1);
   }
   ```

2. **Add batch processing mode:** Add an optional `days` parameter to the tick endpoint so you can advance multiple days in a single API call:
   ```python
   @app.post("/api/simulation/tick")
   async def advance_simulation_tick(days: int = 1, db = Depends(get_db)):
       for _ in range(days):
           simulation_state["virtual_date"] += timedelta(days=1)
           await process_simulation_tick(db, simulation_state["virtual_date"])
   ```

3. **Consider running invoices in parallel** using `asyncio.gather()` in `core_loop.py` instead of a sequential `for` loop.

## Bug 6: Compliance Score Is Always 100%

### Root Cause
Two compounding issues:

1. **The `compliance_verdict` is never saved to the `audit_log` DB table.** Look at [core_loop.py](file:///c:/PROGRAMER's%20FOLDER/Projects/RazorPay/RevenueGuard/src/engine/core_loop.py#L56-L65):
   ```python
   await log_audit_event(
       db, invoice.id, 
       entry["event_type"], 
       entry["reasoning"], 
       entry["action"], 
       virtual_date, 
       rule_applied=entry.get("rule"), 
       content_snapshot=entry.get("content")
   )
   ```
   Notice there is **no `compliance_verdict` parameter** being passed! The `log_audit_event` function in [crud.py](file:///c:/PROGRAMER's%20FOLDER/Projects/RazorPay/RevenueGuard/src/persistence/crud.py#L75-L88) doesn't accept a `compliance_verdict` parameter either.

2. **The compliance stats endpoint** ([dashboard_api.py](file:///c:/PROGRAMER's%20FOLDER/Projects/RazorPay/RevenueGuard/src/dashboard_api.py#L253-L268)) queries `AuditLog.compliance_verdict != None`, which returns 0 rows because the field is never populated. Then:
   ```python
   rate = (passed / total * 100) if total > 0 else 100.0  # ← total is 0, so rate = 100%
   ```

3. **Even if the API key is missing**, the compliance judge ([compliance_judge.py](file:///c:/PROGRAMER's%20FOLDER/Projects/RazorPay/RevenueGuard/src/ai/compliance_judge.py#L25-L27)) returns `{"verdict": "PASS"}` as a mock. So the judge never fails.

### Fix
1. Add `compliance_verdict` parameter to `log_audit_event()` in `crud.py`.
2. Pass `compliance_verdict` from the audit entry in `core_loop.py`.
3. In `nodes.py`, add a `"compliance_verdict"` key to each audit entry dict where compliance is checked.
4. Make the mock compliance judge occasionally fail (e.g., 20% of the time) for demo purposes when the API key is missing.
